# 1.1 — LLMs: Capabilities & Limitations

> Module: 01 — AI Fundamentals · First taught: 2026-11-26 · Last updated: 2026-11-26

## TL;DR
An LLM predicts the next token from whatever is in its context, so its output is just as fluent when it's wrong as when it's right. Anything not in context (private conventions, APIs released after the training cutoff, company policy) gets guessed. Output is probabilistic, so a single good run proves little; reliability comes from the checks you build around the model. Each kind of task should get a verification level matched to where the model is weak, and every check needs an **oracle** (a source of expected answers) that is independent of the code being checked.

## Key Concepts

### One mechanism, fluent either way
Code, plans, explanations, and "reasoning" all come out of next-token prediction. Confident tone is not evidence. Treat every output as a draft from a capable colleague whose work you haven't verified yet.

### Strong vs weak
- **Strong:** reading and summarizing code, translating intent into conventional code, following patterns already in context, explaining errors, drafting tests, plans, and docs.
- **Weak:** facts not in context (your codebase's rules, recent library releases), exact arithmetic and bookkeeping, ambiguous specs (it fills gaps silently), knowing what it doesn't know.

### Training cutoff
Anything newer than the training data has to be supplied through context or tools, for example the installed version from the lockfile plus current official docs. Otherwise the model writes outdated or invented API calls that may still compile.

### Verification tiers
| Tier | Meaning |
|------|---------|
| **A** | Accept after reading the diff |
| **B** | Accept only after a test or type check passes |
| **C** | Don't delegate, or only after supplying the missing context |

### The oracle rule
A check is only as good as its oracle. Expected answers must come from a human or the spec, never from the same model that wrote the code. If they come from that model, the test only proves the model agrees with itself.

### Sensitivity vs correctness of a test
- **Sensitivity (mutation check):** break the *production code* and confirm the test fails. A test you've never seen fail proves nothing. Breaking the *test* (for example, inverting an assertion) only proves it runs.
- **Correctness (independent oracle):** expected values come from the spec, decided before reading the AI's version.
- You need both. A mutation check won't catch a spec misreading that is shared by the code and the test.

### Agent self-check vs your evidence
Let the agent run tests inside its own loop so it can correct itself. Then re-run them yourself. An agent reporting "all tests pass" is a claim; your terminal output is the evidence.

### Specifying a task for an agent
A good implementation prompt states: the goal and its scale, the stack (including the test runner), the exact contract (status codes, response bodies, visible text), acceptance criteria as observable commands, an explicit out-of-scope list, and process checkpoints (plan before writing files, the human commits). Every gap gets filled by the model's defaults.

## Examples

**Rating task types:**
| Task | Tier | Reason → how to verify |
|------|------|------------------------|
| ORM query with filter + pagination | A+B | Conventional code, but off-by-one and NULL/dialect issues only show at runtime → test against a real DB |
| Explain a stack trace | A | Explaining is a strength, but plausibility convinces → make the explanation predict something checkable (open the line; reproduce, fix, re-run) |
| Use a framework's newest API | C → B | Possibly after the cutoff → supply version + current docs, then build and test |
| Rename a prop across many files | A+B or no AI | Mechanical → IDE rename refactor (deterministic) or the type checker |
| Fee calc (7%, 50 minimum, 2 decimals) | B + own oracle | Spec gaps (minimum before or after rounding? rounding mode?) are human decisions → human writes the edge cases; use decimal/integer minor units, not float |
| Apply company policy to reject an item | C | Policy isn't in context; accountability stays with a human |
| Table-driven tests for an existing validator | B + mutation + oracle | Tests lock in current behaviour → break the validator; compare cases to the spec |

**Shared-misreading example:** The spec says "names at most 50 characters." The model writes `len(name) < 50` and a test asserting that a 50-character name is rejected. The test passes, and the mutation check passes too (remove the check → the test fails). The bug survives. Only a human-written case ("50 → accept") catches it.

**Spec-style prompt skeleton:**
```markdown
## Task          — what + scale ("skeleton only")
## Stack         — frameworks + named test runner
## Requirements  — exact contracts (e.g. GET /health → 200 {"status":"ok"})
## Acceptance criteria — commands that must pass; show real output
## Out of scope  — what must NOT be added
## Process       — plan first and wait for OK; human commits
```

## When Not to Use It
- Don't reach for an LLM when a deterministic tool already does the job reliably (IDE refactors, formatters, codegen from schemas). It's cheaper and exact.
- Heavy verification is overkill for throwaway exploration or spikes. Match the tier to the cost of being wrong.
- A written list of verification tiers is a thinking tool. In a real workflow these rules end up enforced through hooks, CI gates, required reviewers, permission settings, and project instruction files, because a rule that lives only in someone's head gets skipped.

## Common Pitfalls
- A common mistake is verifying only **intent** (the plan matches the ticket) and not **output** (the code actually does it).
- A common mistake is "breaking" a test by editing the assertion instead of the production code.
- A common mistake is letting the model write both the implementation and the expected values, then treating a passing test as proof.
- A common mistake is accepting an agent's "done" or "all tests pass" without re-running the checks yourself.
- A common mistake is checking a UI only on the happy path at one screen size. Loading, error, empty, and long-content states, plus several breakpoints, are where generated UI usually breaks.
- A common mistake is assertions that can't fail independently, for example re-checking text that the query already matched on.

## Quick Recall

4. Why should the agent run the tests *and* you re-run them?
5. When is an IDE refactor a better choice than an LLM?
