# 6.5 Test-Driven & Verification-Driven Development

- Test-driven development writes a failing test first, then the code that makes it pass, then refactors. With an agent, the test becomes an executable specification and an objective stop condition for the loop.
- Verification-driven development generalizes the idea: before work starts, decide what evidence will prove it is done, and build the workflow so that evidence is produced.
- The test levels each catch different things. Unit tests: logic in isolation, fast. Integration tests: components working together, including the database. Contract tests: both sides of an interface honoring the agreement. End-to-end tests: a real user flow through the whole system.
- Static checks — type checking, linting, the build — are the cheapest verification and should run on every iteration of the inner loop.
- Regression prevention: every fixed bug gets a test that fails without the fix, and existing tests are run to confirm that nothing else broke.
- With agents, write or review the tests before the implementation and keep the two steps apart. An agent that writes code and tests together can make them agree with each other and still be wrong.
- Test evidence is the output of the run — which tests, how many passed, the failures in full — not the statement that they passed.
- Failure diagnosis is an evidence task: read the actual error, form a hypothesis, confirm it, then fix. Changing code until the red turns green is not diagnosis.
