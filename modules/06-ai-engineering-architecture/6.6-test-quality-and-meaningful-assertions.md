# 6.6 Test Quality & Meaningful Assertions

- A test is only worth what it can detect. A suite can be green and worthless if its tests would still pass when the behavior is broken.
- A meaningful assertion checks an outcome the requirement cares about — the returned value, the stored state, the emitted event, the error for invalid input — not merely that the code ran without throwing.
- AI-generated tests have typical weaknesses: asserting what the implementation happens to do rather than what it should do, mocking so much that nothing real is exercised, covering only the happy path, and duplicating the implementation's logic inside the test.
- A test derived from the implementation reproduces its assumptions: if the code has the bug, the test certifies the bug. Derive tests from the specification and acceptance criteria.
- The practical check: break the code on purpose — or revert the fix — and see whether the test fails. A test that cannot fail is not a test.
- Coverage numbers measure what was executed, not what was checked. High coverage with weak assertions is a common result of asking an agent to "increase coverage".
- Watch for tests being changed to pass: weakened assertions, removed cases, skipped tests, widened tolerances. Review test diffs with more suspicion than code diffs.
- Good tests read as documentation of behavior: a name stating the scenario and expected result, a clear arrangement, one behavior per test, and no dependence on other tests' state.
