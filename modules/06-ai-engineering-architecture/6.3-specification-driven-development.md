# 6.3 Specification-Driven Development

- In specification-driven development, a written specification — not a chat message — is the source of truth for what is built. The implementation, the tests, and the verification all refer back to it.
- It matters more with AI than without: an agent will build exactly what the text allows, filling every gap with a plausible assumption. Ambiguity that a human colleague would query becomes a silent guess.
- Requirement decomposition: break a business goal into small requirements that can each be implemented and verified, each with an identifier.
- Functional requirements say what the system does; non-functional requirements say how well — performance, security, accessibility, auditability. The second group is what agents omit unless it is written down.
- Acceptance criteria make each requirement checkable: concrete conditions, including the unhappy paths — invalid input, missing permission, wrong state.
- A technical specification turns the requirements into a design: affected components, data model and API changes, key decisions, and the test strategy. It is what the human approves before implementation.
- AI is useful for producing the specification — drafting, finding gaps, asking clarifying questions — but the human owns it. An AI-written specification approved unread is still a guess.
- Size it to the work: a one-line fix needs a sentence and a test; a new feature needs requirements, criteria, and a plan. A ceremony-heavy process for small changes will be abandoned.
