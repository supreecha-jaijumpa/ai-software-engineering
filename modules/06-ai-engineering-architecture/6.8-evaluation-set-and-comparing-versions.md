# 6.8 Building an Evaluation Set & Comparing Workflow Versions

- An evaluation set is a fixed collection of representative tasks with known success criteria, used to test a workflow the way a test suite tests code.
- Representative means it resembles your real work: a bug fix, a small feature, a refactor, an API change, a frontend change, a task with an ambiguous requirement, and one that should end in escalation rather than code.
- Each task needs a starting state that can be reproduced (a commit), a written task description, acceptance criteria, and a way to score the result — ideally tests that were not shown to the agent.
- Take a baseline first: run the current workflow on the set and record quality, time, rework, and tokens. Without a baseline, no later number means anything.
- Change one thing at a time — a new rule, a hook, a reviewer step — and re-run. If several things change together, you cannot tell which one helped.
- Results vary between runs because the model is not deterministic. Repeat runs where it matters and distrust small differences from a handful of tasks.
- Keep the set small enough to run regularly — five to ten tasks is a useful start — and add a task whenever a real failure exposes something the set did not cover.
- Document each comparison: what changed, what was measured, what improved, what got worse, and the decision. Removing a change that did not help is a successful outcome.
