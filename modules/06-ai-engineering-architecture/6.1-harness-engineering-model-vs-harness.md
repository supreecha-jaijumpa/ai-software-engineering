# 6.1 Harness Engineering — Model vs Harness

- The model supplies language and problem-solving capability. The harness is the system around it that supplies context, tools, constraints, feedback, and control. What you experience as "the AI's behavior" is the two together.
- Harness components: instructions and context; tools and integrations; permissions and approval boundaries; sandboxing and execution constraints; deterministic scripts and quality gates; state, logs, and recovery; human oversight and escalation.
- Claude Code is a harness. Everything from Levels 2–5 — `CLAUDE.md`, skills, hooks, permissions, subagents, loops, task state — is harness configuration.
- The same model performs very differently in different harnesses, and the harness is the part you can engineer. Improving it is usually the cheapest route to better results.
- Harness engineering is ordinary systems engineering applied to an unreliable component: assume the component will sometimes be wrong, and design so that errors are detected, contained, and corrected.
- A useful division: let the model do what requires judgment and language; let the harness do what must be exact, repeatable, or enforced.
- When a failure occurs, ask which harness component let it through — missing context, a missing tool, a missing gate, a missing permission, no feedback — instead of only asking for a better prompt.
- Models change and improve; a well-built harness carries over, and a harness tuned around one model's quirks should be re-tested when the model changes.
