# 6.4 Contracts, Traceability & Change-Impact Analysis

- A contract is a precise, shared definition of an interface: API endpoints with request, response, and error shapes; data schemas; event formats; types shared between frontend and backend.
- Contracts let work proceed independently and let it be checked mechanically — schema validation, generated types, contract tests — instead of by reading both sides and hoping.
- Define the contract before implementation and change it only through a visible step. An agent quietly adjusting the contract to fit its implementation breaks every other consumer.
- Traceability links each requirement to the code that implements it and the tests that verify it. It answers "is everything specified actually built and tested?" and "why does this code exist?".
- A lightweight form is enough: requirement identifiers referenced in the plan, in test names, and in the verification report. A matrix of requirement → implementation → test → evidence can be generated from those.
- Traceability exposes two failure types quickly: requirements with no test (unverified) and changes with no requirement (scope creep).
- Change-impact analysis asks what else is affected by a change: callers, dependents, data migrations, other features using the same contract. The feature map from Level 4 is its starting point.
- Have the agent state the expected impact before implementing and compare it with the actual diff afterwards. A large gap between the two means the understanding was wrong.
