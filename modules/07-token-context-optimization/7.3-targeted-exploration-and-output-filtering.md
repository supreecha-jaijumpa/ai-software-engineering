# 7.3 Targeted Exploration & Output Filtering

- Exploration is where most tokens are spent in an unfamiliar codebase. Targeted exploration finds the few relevant files; broad exploration reads many files in the hope that the answer is among them.
- Search before reading: locate candidates by file name and content search, then read only the relevant files — and only the relevant parts of large ones.
- Give the agent starting points when you have them. "The handler is in orders/api and the bug appears on draft submission" saves the whole discovery phase.
- Selective tool use: prefer the narrowest tool that answers the question — a search over a full read, a specific test over the whole suite, a diff over two full files.
- Filter logs and command output before the model sees them: failures only, the last lines of a build, a grep for the error. The full output can go to a file and be consulted when needed.
- Many tools have quiet or summary modes; using them in project scripts fixes the problem once for every future session.
- Avoid repeated exploration: record what was learned — in a feature map or a state note — so that the next session, or another agent, does not pay for the same discovery again.
- Broad reading is sometimes right — for example when designing a change that cuts across the system. Then do it on purpose, preferably in a subagent, so that the main context receives the conclusions rather than the files.
