# 4.3 Deterministic Checks vs Model Judgment

- A deterministic check gives the same answer for the same input and can fail objectively: tests, type checking, linting, builds, schema validation, a script comparing actual and expected output.
- Model judgment is an evaluation made by an LLM: does this diff match the requirement, is this code readable, is this plan reasonable. It is flexible and it is fallible.
- Use deterministic checks wherever a rule can be expressed as code — they are cheaper, repeatable, and do not get talked into passing.
- Use model judgment where no script can decide: intent, completeness against prose requirements, design quality, missing edge cases. Give it explicit criteria and require cited evidence.
- Never use model judgment as a substitute for a check that could be run. "The reviewer agent believes the tests pass" is worth nothing next to the test run.
- Order them sensibly: deterministic gates first (fast and cheap), model review on what survives, human review on what matters most.
- Model judges share the model's blind spots and are biased toward agreement, especially when judging their own work or when shown the author's reasoning. Independence and a skeptical brief improve them.
- A good verification report labels its claims: verified by command (with output), judged by model (with reasoning), or not verified. Mixing the three is how false confidence is created.
