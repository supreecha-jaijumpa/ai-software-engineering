# 4.11 /verify-feature — Evidence-Based Verification

- `/verify-feature` is the verification step of the workflow: it checks the implementation against the requirement and reports a verdict backed by evidence. It verifies; it does not fix.
- Inputs: the task's acceptance criteria, the feature map, and the current code. If the acceptance criteria are missing or untestable, the correct result is `blocked`, not an improvised definition of success.
- For every criterion it produces one of: verified (with the evidence — command and output, test name, observed behavior), failed (with what was observed instead), or not verifiable (with the reason).
- It runs the deterministic checks first — relevant tests, type check, lint, build — and only then applies judgment to what scripts cannot decide, such as whether the diff covers the whole requirement.
- It also checks scope: are there changes unrelated to the task, and are the dependents named in the feature map still working?
- Three outcomes drive the workflow: pass → human review; fail → diagnose, fix, and verify again within the retry bound; blocked → report and request a human decision.
- Keep it independent of the implementation step — a fresh context or a separate read-only agent — so that it does not inherit the implementer's belief that the work is done.
- The report is the product: criteria table, evidence, checks run, problems found, what was not verified. "All good" without evidence is a failed verification.
