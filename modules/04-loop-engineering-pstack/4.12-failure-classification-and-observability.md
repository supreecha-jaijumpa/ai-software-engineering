# 4.12 Failure Classification & Workflow Observability

- Not all failures deserve the same response. Classifying a failure before reacting is what separates a correction loop from repeated guessing.
- A practical classification: implementation defect (code is wrong — fix and re-verify), test defect (the test is wrong — needs care and usually review), missing or ambiguous requirement (escalate), environment or dependency problem (report as blocked), transient failure (retry unchanged, once), out of scope (stop and report).
- Each class maps to an action and a retry rule. Only implementation defects and transient failures should be retried automatically; the others need a human or a change of plan.
- Misclassification is common and costly: treating a missing requirement as a code defect produces confident implementations of a guess; treating a real defect as a flaky test hides a bug.
- Observability means the workflow leaves enough trace to answer afterwards: what stage ran, what was attempted, what was observed, how long it took, and why it stopped.
- A minimal execution log — timestamp, task, stage, action, result, attempt number — is enough to see patterns: which stage fails most, where retries are spent, which tasks get blocked.
- Test the workflow with simulated failures: a failing test, a missing requirement, a blocked dependency. The workflow passes if it classifies each correctly and stops safely.
- Those patterns are the input for improving the workflow — and the starting point of the evaluation work in Level 6.
