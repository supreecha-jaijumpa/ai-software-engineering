# 4.9 Control App — Tasks, Stages & Task States

- The Control App is the part of the workflow that knows which tasks exist, what stage each is in, and what is allowed to happen next. It turns an open-ended conversation into a tracked process.
- A task record holds: an identifier, the requirement, scope and out-of-scope, acceptance criteria, the current state, links to the feature map and the plan, and a history of state changes.
- Example states: `draft` (requirement captured, not yet analyzed), `planned` (plan written), `approved` (a human accepted the plan), `implementing`, `verifying`, `blocked` (waiting for a decision or dependency), `completed`.
- States are useful only with defined transitions. `implementing` requires `approved`; `completed` requires a passing verification and human review; `blocked` records what it is waiting for and which state to return to.
- Gates are transitions that need something external: a human approval, or passing checks. They are where control is exercised, so they must not be skippable by the agent's own decision.
- The state is a fact that tools and agents can read: an implementation skill can refuse to start on a task that is not `approved`, and a verification skill can refuse a task that was never implemented.
- Start with the simplest implementation that makes the state explicit and durable — a file per task. Build tooling only when manual updates become the bottleneck.
- A task that sits in `implementing` or `verifying` for many attempts is information: the scope was too large, the criteria were unclear, or the loop lacks the feedback it needs.
