# 4.2 Feedback Loops & Verification Loops

- A feedback loop gives the agent information about the effect of its own actions so that it can correct them: compiler errors, failing tests, lint output, a rendered screenshot, an API response.
- The quality of an agent's work is limited by the quality of its feedback. An agent that cannot run the tests is writing code blind, however capable the model is.
- Fast, specific feedback is worth more than slow, complete feedback: a targeted test in seconds allows many corrections; a full suite in twenty minutes allows few.
- A verification loop is a feedback loop aimed at the acceptance criteria — it answers "is the goal met?" rather than "did this step break something?".
- Inner and outer loops nest: inner (edit → type check → unit test) runs many times per task; outer (feature → acceptance checks → review) runs once or a few times.
- Feedback must be trustworthy. If the agent can make the signal pass without fixing the problem — deleting a test, weakening an assertion, skipping a check — it sometimes will.
- Protect the signal: state that tests may not be weakened to pass, review test changes separately, and keep some checks outside the agent's reach.
- When a workflow performs poorly, first ask what feedback the agent had access to — adding a missing feedback source usually helps more than refining the prompt.
