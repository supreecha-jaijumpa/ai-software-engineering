# 4.10 Feature Map — Scope, Dependencies & Impact

- A feature map is a compact description of what a feature consists of and what it touches: modules and files, data models, APIs, UI entry points, external services, tests, and the dependencies between them.
- It exists to answer, before any code changes: what is in scope, what is affected indirectly, and what could break.
- For an existing feature it is produced by exploration — tracing the flow from entry point to storage — and it records findings with file references, so they can be checked rather than believed.
- Useful sections: purpose, entry points, components and their roles, data flow, dependencies (what it uses) and dependents (what uses it), existing tests, risks, and unknowns.
- The unknowns section matters: an honest "not yet verified how notifications are triggered" is worth more than a confident guess.
- It serves as context for later stages — planning and implementation load the map instead of re-exploring the codebase, saving tokens and keeping every stage on the same understanding.
- It is also the basis for impact analysis and for deciding what verification must cover: every dependent listed in the map is a candidate for a regression check.
- A map goes stale when the code changes. Record when it was produced, update it as part of finishing the feature, and treat an old map as a starting hypothesis to verify.
