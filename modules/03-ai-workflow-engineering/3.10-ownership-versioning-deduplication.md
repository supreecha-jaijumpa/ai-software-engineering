# 3.10 Naming, Ownership, Versioning & Deduplication of AI Instructions

- AI instructions are part of the system's behavior, so they need what code needs: clear names, an owner, version control, review, and removal when obsolete.
- Naming: a file or skill name should say what it is for, in the words people use. Consistent verb-noun names (`verify-feature`, `plan-implementation`) make skills discoverable for both humans and the model.
- Ownership: every instruction file has someone who decides what it says. Unowned instructions accumulate, because adding a line is easy and nobody feels entitled to delete one.
- Versioning: keep instructions in the repository with the code they describe, change them through review, and record why a rule was added — a rule without a reason cannot be safely removed later.
- Duplication is the main disease. The same convention stated in `CLAUDE.md`, a rule, and a skill will drift until the copies contradict, and the model then follows one of them unpredictably.
- One fact, one home: state each convention once and point to it from elsewhere. If a tool (linter, formatter, type checker) already enforces it, the tool is the home and the instruction is unnecessary.
- Contradictions are often invisible to their authors — a user-level preference against a project rule, an old skill against a new convention. Audit by searching for the same topic across all instruction files.
- Maintenance signals: a rule added after an incident (keep, with the reason), a rule nobody can explain (candidate for deletion), and a rule the model keeps ignoring (rewrite it, enforce it, or drop it).
