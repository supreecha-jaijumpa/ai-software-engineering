# 3.8 Skill Design — the Quality Checklist

- A skill is a small program written in prose. It deserves the same design care as a function: a clear contract, defined inputs, ordered steps, error handling, and a defined result.
- Name and description / trigger: say what it does and when to use it, in the vocabulary of real requests. This is the only part always in context, and it decides whether the skill ever loads.
- Objective and expected output: state what "finished" looks like and the form of the result — a report, a plan file, a set of changes.
- Required inputs and preconditions: what must be given or true before starting (a requirement text, a clean working tree, an approved plan) and what to do if it is missing — usually stop and ask.
- Steps in a sensible order, each one an action with an observable result. Constraints and things not to do: scope limits, files not to touch, actions needing approval.
- References loaded only when needed: keep the main file short and move detail (templates, checklists, examples) into supporting files that are named with the condition for reading them.
- Verification and failure handling: how the skill checks its own result with real evidence, how many attempts it may make, and when it reports a blocker instead of guessing.
- Completion report: what was done, what evidence supports it, what was not done, and what the human should look at. Then test the skill like code — on a real task, in a fresh session, including a case where a precondition is missing.
