# 3.4 Context Isolation & Context Pollution

- Context pollution is content in the window that is irrelevant, outdated, or wrong for the current task and that degrades the work: an abandoned approach, a stale error, another feature's requirements, a huge log.
- The model cannot reliably ignore what it has seen. A rejected design discussed for twenty turns keeps pulling later answers back toward it.
- Common sources: one long session used for unrelated tasks, verbose command output, exploratory reading of files that turned out to be irrelevant, repeated failed attempts, and contradictory instruction files.
- Isolation is the countermeasure — keep separate concerns in separate contexts: a fresh session per task, a subagent for exploration, a separate reviewer that has not seen the implementation reasoning.
- Isolation also improves independence: a reviewer sharing the implementer's context inherits its assumptions and tends to confirm them.
- The cost of isolation is the handoff. Whatever the isolated context needs must be passed explicitly, so isolation forces you to write down goals and contracts — which is usually a benefit.
- Cheap hygiene: clear between tasks, restart after two failed corrections of the same problem instead of adding a third, and filter output before it enters the window.
- Symptoms to watch for: the model refers to things from an earlier task, re-applies a fix you rejected, or follows a rule that belongs to a different part of the codebase.
