# 3.1 Context Architecture & Context Boundaries

- Context architecture is the deliberate design of what knowledge exists for the AI, where it lives, and when it enters the context window — the same way software architecture decides where code lives and what depends on what.
- Without a design, context grows by accident: every problem adds a paragraph to `CLAUDE.md` until the file is long, contradictory, and mostly irrelevant to any given task.
- A boundary answers "what must this unit of work know, and what must it not see?" — a frontend fix does not need the database migration guide, and a reviewer does not need the implementation chat history.
- Each piece of knowledge needs three decisions: its home (one file, one owner), its loader (always, by path, by trigger, on request), and its lifetime (permanent, per feature, per task).
- Familiar design forces apply: cohesion (one topic per file), low coupling (files that can change independently), and a single source of truth (no fact stated twice).
- The cost model is specific to AI: always-loaded content is paid on every turn, and irrelevant content does not just cost tokens — it reduces the chance that the relevant instruction is followed.
- A context architecture is good when a new teammate can answer, for any file, "why does this exist and what loads it?" — and when deleting a file has a predictable effect.
- Start by drawing what is loaded today for a typical task. Most first audits find that the majority of loaded context is unrelated to the work being done.
