# 2.10 Permissions, Tool Approvals & Safe Execution

- Permissions decide which tool calls run without asking, which require your approval, and which are refused. They are enforced by the harness, so they hold even when the model is confused or manipulated.
- Rules are written per tool, optionally with a pattern — for example allowing a specific test command, asking before `git push`, or denying reads of `.env` files — and are grouped into allow, ask, and deny lists. Deny wins over allow.
- Rules live in settings files at user, project, and local scope, and can be inspected and edited with `/permissions`.
- Permission modes change the default posture for a session: asking before edits and commands, auto-accepting file edits, a plan mode that analyzes without changing anything, and a bypass mode that skips prompts and belongs only in isolated environments.
- The trade-off is real: too many prompts create approval fatigue and people stop reading them; too few and one bad step runs unattended. Allow the safe and frequent, keep prompts for the risky and rare.
- Decide by reversibility and blast radius. Reading files and running tests are cheap to allow; deleting, force-pushing, publishing, migrating a database, or sending anything outward should need a human.
- Shell pattern rules are not a security boundary by themselves — commands can be chained or rewritten to slip past a pattern. Sandboxing and restricted credentials are the stronger controls.
- Checkpoints let you rewind file edits made in a session, but not side effects outside it: a pushed commit, a sent message, or a dropped table stays done.
