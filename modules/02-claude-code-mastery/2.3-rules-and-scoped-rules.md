# 2.3 .claude/rules/ & Scoped Rules

- `.claude/rules/` holds Markdown files with focused instructions, one topic per file (for example `testing.md`, `api-design.md`), so conventions do not pile up in one large `CLAUDE.md`.
- A rule without path scoping is loaded at session start like `CLAUDE.md` — it is an organizing tool, not a saving.
- A rule can be scoped with a `paths` frontmatter field containing glob patterns; it then applies only when Claude works with matching files — for example frontend conventions only for `src/web/**`.
- Scoping is the point: backend sessions do not pay for frontend rules, and each rule arrives exactly when it is relevant.
- Rules are for constraints and conventions ("API handlers validate input with the shared schema"), not for multi-step procedures — a procedure is a skill.
- Like all instructions, rules are guidance. A convention that can be checked mechanically (formatting, lint, forbidden imports) is better enforced by the linter or a hook, with the rule explaining the intent.
- User-level rules (`~/.claude/rules/`) apply to all your projects; project rules are shared through version control.
- Maintenance cost: every rule needs an owner and a reason. Rules that duplicate `CLAUDE.md` or each other eventually contradict — keep one home per convention.
