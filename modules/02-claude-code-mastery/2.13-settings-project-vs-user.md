# 2.13 Settings — Project vs User Configuration

- Claude Code is configured through `settings.json` files at several scopes: user (`~/.claude/settings.json`), project shared (`.claude/settings.json`, committed), project local (`.claude/settings.local.json`, not committed), and organization-managed policy.
- More specific scopes override more general ones, and managed policy overrides everything — that is how an organization enforces limits that an individual cannot loosen.
- Settings hold the enforced part of the configuration: permission rules, hooks, environment variables, model choice, and similar switches. Instructions in Markdown are advice; settings are behavior.
- The same scoping idea applies to the other mechanisms: skills, agents, rules, and MCP servers each have a personal location and a project location.
- Put in the project scope what every contributor needs to work safely and consistently: shared permission rules, team hooks, project MCP servers.
- Put in the user scope what is personal preference, and in the local scope what is specific to your machine or experimental — and never commit secrets to any of them.
- A committed settings file is executable policy for everyone who opens the repository, and hooks in it run on their machines. Review changes to it as carefully as changes to CI configuration.
- When behavior is surprising, ask which scope is winning: an unexpected permission prompt or hook usually comes from a settings file you forgot about.
