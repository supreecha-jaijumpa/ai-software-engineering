# 1.4 Context Window vs Persistent Project Knowledge

- The context window is working memory: it exists for one session and is gone, or compacted, afterwards. Persistent project knowledge lives in files, version control, and tools.
- Anything you explained only in chat is lost at the end of the session. If it should survive — a convention, a decision, the state of a task — it must be written somewhere durable.
- Persistent knowledge only helps once it is loaded. A perfect architecture document that is never read into context has zero effect on the model's behavior.
- This creates two separate design questions: where does knowledge live (files, docs, tickets), and when does it enter the context (always, on demand, or never)?
- Always-loaded files cost tokens on every turn of every session, so they should hold only what is needed almost every time.
- Persistent knowledge goes stale. A wrong instruction that is always loaded is worse than no instruction — the model will follow it confidently.
- Typical split: stable essentials in an instruction file, detailed references loaded on demand, task state in a short handoff note, and everything else discovered by search.
- Practical consequence: at the end of a session ask "what must the next session know?" and write only that down.
