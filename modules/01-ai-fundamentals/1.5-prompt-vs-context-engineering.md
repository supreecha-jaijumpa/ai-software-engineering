# 1.5 Prompt Engineering vs Context Engineering

- Prompt engineering is how the task is communicated: the goal, the constraints, the expected output, and the definition of done.
- Context engineering is what information, constraints, examples, and tools are made available when the model works: which files it has seen, which instructions are loaded, which tools exist, and what state it knows about.
- Verification is the third leg: how correctness is established independently of the model's confidence. A good prompt and good context still produce a draft, not a fact.
- A well-phrased prompt cannot compensate for missing context — the model fills gaps with plausible defaults, which is where "it ignored our conventions" comes from.
- More context is not automatically better. Relevant, current, well-structured context is better; irrelevant or stale context dilutes attention and costs tokens.
- A strong task brief names the goal, the scope (and what is out of scope), pointers to the relevant code, the conventions to follow, and acceptance criteria that can be checked.
- Acceptance criteria turn "looks right" into something observable: a test that passes, a command that returns a value, a behavior that can be demonstrated.
- Practical consequence: when output is poor, diagnose which leg failed — unclear task, missing or noisy context, or no verification — before rewriting the prompt.
