# 1.6 System Instructions & Instruction Hierarchy

- A model call usually has layers: a system prompt set by the application, messages from the user, and results returned by tools. They do not carry the same authority.
- System instructions define the role, the rules, and the available tools; user messages carry the task; tool results are data to be used, not orders to be followed.
- In a coding tool there are more layers still: the tool's own system prompt, organization policy, your personal instructions, project instruction files, and the current conversation.
- More specific and more recent instructions tend to win when they conflict, but conflicts are resolved by a probabilistic model — not by a deterministic rule engine. Contradictions lead to inconsistent behavior.
- Instructions are guidance, not enforcement. "Never run this command" in an instruction file lowers the probability; a permission rule or a hook actually prevents it.
- Vague or emphatic instructions ("be careful", "ALWAYS", "IMPORTANT") work worse than specific ones with a reason and an observable condition.
- Every always-loaded instruction competes for attention with every other one; a long list makes each item less likely to be followed.
- Practical consequence: keep instructions few, specific, and non-contradictory, and move anything that must always hold into a deterministic control.
