# 1.7 Tool Calling & Tool-Use Cycles

- A model cannot act by itself. With tool calling, the application describes tools (name, purpose, parameters) and the model may answer with a structured request to use one.
- The cycle: the model requests a tool → the application decides whether to run it and executes it → the result is sent back as new input → the model continues. One user request can involve many cycles.
- The application, not the model, executes the tool. That is where permissions, sandboxing, and approval prompts live — and why they can be trusted more than instructions.
- Tool descriptions are part of the context and cost tokens on every turn; many tools with vague descriptions make tool selection worse, not better.
- Tool results become context. Large or noisy results fill the window, and results from untrusted sources (web pages, issue text, file contents) may contain text that looks like instructions.
- Good tools are narrow, clearly described, and return compact, relevant output; a tool that dumps everything forces the model to do the filtering inside its context.
- Errors are also results: a failing command with a clear message is useful feedback, and reading it is how the model self-corrects.
- Practical consequence: when the model makes a strange decision, read the tool calls and their results — the cause is usually visible there.
