# 5.4 Parallel vs Sequential Execution

- Parallel execution shortens elapsed time; it does not reduce total work, and it usually increases total tokens. It is a trade of cost for speed.
- Work can run in parallel when tasks are independent or separated by a stable contract — neither needs the other's result, and they do not modify the same things.
- Good candidates: independent research questions, several reviews of the same read-only diff (security, performance), frontend and backend work after the API contract is agreed, separate modules with clear ownership.
- Poor candidates: several agents editing the same files, frontend work against an API that is still changing, schema changes running alongside the code that depends on them, and any task whose steps are inherently sequential.
- Read-only work is nearly always safe to parallelize; write work needs isolation (separate files, or separate working directories) and an integration plan.
- The contract is what makes parallel implementation possible. Agree on it and write it down first — the endpoint shapes, the types, the error cases — then split.
- Parallel work hides problems until integration. Two agents can each succeed against their own assumptions and still fail together.
- When unsure, go sequential: the later task benefits from what the earlier one learned, and the cost of waiting is usually smaller than the cost of reconciling.
