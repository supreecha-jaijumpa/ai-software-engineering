# 5.1 Agent Roles & Responsibility Boundaries

- A role is a bounded responsibility given to an agent: what it is for, what it may read and change, which tools it has, and what it must deliver.
- A boundary is useful when it is enforceable — a reviewer without edit tools, a researcher without shell access — not merely described in a prompt.
- Roles earn their place in three ways: a different context (a fresh view, or a large exploration kept out of the main window), different permissions (read-only versus write), or different instructions (a security checklist versus an implementation guide).
- A role that differs only by name ("senior backend expert") adds cost without changing behavior. A persona is not a boundary.
- Each role needs one clear owner of each outcome: if two agents are both "responsible for tests", neither is.
- Fewer roles are better. Every additional role adds a handoff, and every handoff loses information. Start with one implementer and one independent checker and add a role only when a specific failure calls for it.
- Typical boundaries that hold up: research is read-only and returns findings with file references; implementation changes only files in its assigned scope; review reports and never fixes.
- Write each role as a short contract — purpose, inputs, allowed actions, forbidden actions, output format, when to stop and report — and you have most of an agent definition.
