# 5.9 Merge Conflicts & Integration Strategy

- Integration is where parallel work is paid for. Each branch can be correct alone and wrong together — and git reports only textual conflicts, not semantic ones.
- A textual conflict is two changes to the same lines. A semantic conflict merges cleanly and breaks behavior: one branch renames a function, another adds a new call to the old name.
- Prevention beats resolution: split work by file ownership, agree on contracts first, keep parallel tasks short-lived, and integrate often rather than at the end.
- Decide the integration order in advance — typically the foundational change first (schema, shared types, contract), then the branches that depend on it, re-based on the result.
- Assign integration to one owner, usually the orchestrator or the human. Workers resolving conflicts in each other's code without the context behind it is how correct work gets silently damaged.
- Resolving a conflict requires understanding the intent of both sides. Letting an agent "just fix the conflicts" without the tasks' briefs invites it to pick a side arbitrarily.
- After every integration, run the full verification again: the build, the tests of all merged parts, and the acceptance criteria of the whole feature. Verification of the parts does not transfer to the whole.
- If integration is repeatedly painful, the decomposition was wrong — the tasks were more coupled than assumed. Go back to the dependency graph rather than getting better at merging.
