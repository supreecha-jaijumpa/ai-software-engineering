# 5.2 Orchestrator Patterns

- An orchestrator is the agent — or the human, or a script — that holds the goal, breaks the work down, hands pieces to workers, and integrates what comes back.
- Orchestrator-workers: one coordinating context delegates to specialists and combines their results. It is the most common pattern, and the one Claude Code's subagents support directly.
- Pipeline: fixed stages in sequence (analyze → plan → implement → verify), each consuming the previous stage's artifact. Predictable and easy to debug; little flexibility.
- Fan-out / fan-in: the same kind of task is run several times in parallel (review several modules, research several questions) and the results are merged. The merge step is where quality is won or lost.
- Maker-checker pair: one agent produces, an independent one verifies, with a bounded number of rounds.
- The orchestrator should stay thin: clarify the goal, decompose, brief, integrate, verify. An orchestrator that also implements fills its own context and loses the overview.
- The orchestrator remains responsible for the result. Workers return claims; integrating without verifying them means multiplying unverified work.
- Deterministic orchestration — a script or a fixed workflow deciding the order — is more reliable than letting a model decide the control flow, whenever the steps are known in advance.
