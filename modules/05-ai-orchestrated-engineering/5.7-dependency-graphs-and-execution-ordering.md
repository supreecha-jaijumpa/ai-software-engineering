# 5.7 Dependency Graphs & Execution Ordering

- A dependency graph lists the tasks and which ones must finish before others can start. It turns "can these run in parallel?" from intuition into something you can read off a diagram.
- Build it from real dependencies: the schema before the code that queries it, the API contract before both its implementation and its consumer, the implementation before its verification.
- Tasks with no path between them can run in parallel; a task with unfinished predecessors must wait. The longest chain determines the minimum elapsed time, however many agents are available.
- The graph exposes false parallelism: if every task depends on the previous one, adding agents adds cost and nothing else.
- Introducing a contract cuts a dependency: frontend and backend both depend on the agreed contract instead of on each other, which is what allows them to proceed side by side.
- Cycles mean the decomposition is wrong — two tasks that each need the other's result are really one task, or are missing a shared contract.
- Order by risk as well as by dependency: do the uncertain, assumption-testing task early, so that a surprise changes the plan before parallel work has been spent on it.
- Keep the graph small and written down — a short list of tasks with "depends on" is enough — and update it when a task reveals a dependency nobody anticipated.
